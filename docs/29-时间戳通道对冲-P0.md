# 29 - 时间戳通道对冲（P0）

> 目标：把"guest 用 rdtsc 前后包一条被拦截的指令"这个最省事的虚拟化检测手段打掉。
> 范围：只动时间戳通道，不碰 EPT/Hook/断点语义。
> 结论先说：**改动全部在 VT_Driver 内部，未新增任何 exit 类型，性能开销等于 0 次额外 VM-exit。**

---

## 1 检测面在哪儿

反作弊（以 ACE 为例）不需要任何内核权限就能测虚拟化：

```
t0 = rdtsc();  cpuid(eax=0, 或者 rdmsr 任意一条);  t1 = rdtsc();
delta = t1 - t0;   // 裸机 100~300 cycle，被 VM-exit 接管后 2000~20000 cycle
```

同一手法还适用于 `rdtsc → rdtsc`（测 exit 频率）、`rdtsc vs rdtscp`（测时间通道是否分裂）。
本项目的 VT 层已经挡住了 CPUID 叶、VMX capability MSR、CR4.VMXE、KUSER_SHARED_DATA 这些**状态型**证据，
但**时间型**证据一直是裸的——原因很简单：`hide_vm_exit_overhead()` 从定义到删除都没有任何调用点，
`vcpu->tsc_offset` 写进去之后也从没被写进 VMCS，整条补偿链路是死代码。

证据（改前）：

| 事实 | 位置 |
| --- | --- |
| `use_tsc_offsetting = false`，VMCS 的 TSC_OFFSET 根本不生效 | `Vmcs/VmcsControls.cpp:77` |
| `tsc_offset` 只在 `VmExitCommon.cpp:333/345` 被写，全仓无任何读取点 | `VmExit/VmExitCommon.cpp` |
| `hide_vm_exit_overhead()` 定义了但没人调用 | `VmExit/VmExitCommon.cpp:304` |
| RDTSC 处理直接返回 `__rdtsc()`，即 handler 当下的物理时间 | `VmExit/VmExitInstruction.cpp:150` |

---

## 2 改法：一条时间真相 + 全局偏移

### 2.1 核心恒等式

```
guest 可见 TSC = VM-exit 入口 TSC + 全局偏移
全局偏移     = -(所有时间敏感 exit 在 root 里消耗的 TSC 时间之和)
```

为什么这样能把差值对干净（记 `E_n` 为第 n 次 exit 的入口 TSC，`C_n` 为它的 handler 耗时）：

```
read_n     = E_n     + O_n          其中 O_n = -(C_0 + ... + C_{n-1})
read_{n+1} = E_{n+1} + O_{n+1}      O_{n+1} = O_n - C_n
差值        = (E_{n+1} - E_n) - C_n
```

而 `E_{n+1} - E_n` 里正好包含 `C_n`（handler 时间）+ 硬件 entry/exit 延迟 + guest 真正执行的时间。
两者相减，handler 时间被完整抵消，只剩下：
**硬件 entry/exit 延迟（每核恒定常量，两次采样互相抵消）+ guest 真正执行的时间。**

这就是裸机看到的东西。

### 2.2 为什么偏移必须全局共享

如果每个 vCPU 各自累计自己的偏移，多核 TSC 会互相漂移（谁 exit 多谁跑得慢），
而"多核 TSC 不同步"本身就是比 VM-exit 更明显的 hypervisor 证据。
所以偏移放在 `__vmm_context` 里，全部逻辑处理器共享一份，用 `InterlockedExchangeAdd64` 原子递减。

### 2.3 为什么必须加单调护栏

多核同时改同一个偏移时，某个核可能在两次采样之间被别人扣掉了更多时间，导致 `visible` 变小。
时间倒退对 Windows 时间子系统是致命的（比暴露虚拟化危险得多），所以每个 vCPU 记一个
`last_visible_tsc`，宁可短暂冻结也不允许回退。

### 2.4 为什么只对"时间敏感 exit"扣，而不是全部

EPT violation 在本项目里是常态（所有 hidden hook 都靠它）。如果无差别地对每一次 exit 扣时间，
guest 时钟会比真实时间越走越慢（几小时的调试能差出十几秒），这本身就是可测特征，
还会让游戏内的计时、心跳、反作弊自身的 tick 全部失真。
所以沿用已有的 `hide_vm_exit_overhead` 标记位——它只由 CPUID / RDMSR / WRMSR / XSETBV /
MOV CR / RDTSC / RDTSCP 这些"被模拟的指令"置位，EPT violation 一律不扣。

### 关于 `vm_exit_ref_tsc_overhead`

`account_vm_exit_overhead()` 里预留了这个标定量（默认 0）：
handler 时间可以被测量并扣掉，但**硬件 VM-entry/VM-exit 延迟在 root 里测不到**。
两者都不扣的时候，guest 在 `rdtsc;cpuid;rdtsc` 里仍能看到约等于硬件延迟的固定开销（通常几百 cycle）。
如果实测发现 CPUID 包裹开销还明显高于裸机，可以在真实机器上标定一次，把这个值填进
`vcpu->vm_exit_ref_tsc_overhead`（每核一个），每核每次对账都会额外扣掉这个常量。
填错的后果只是 guest 时钟略快或略慢，不会蓝屏。

## 4 一个必须更正的结论

之前判断"RDTSCP 没被拦截、可以拿 RDTSC 与 RDTSCP 做差分"是**不完整**的：

- 本仓库当前是 `_MINIMAL` 配置（`vmcs.h` / `VmcsFields.h` 顶部写死 `#define _MINIMAL`），
  `rdtsc_exiting = false`，所以 **RDTSC 与 RDTSCP 都不拦截**，两者都直接读物理 TSC；
- 也就是说"通道分裂"在**当前配置下并不存在**——真正的问题不是分裂，而是两条通道都诚实暴露了
  CPUID/MSR 模拟耗时；
- 也因此，本配置下时间伪装**只能**靠硬件 TSC offsetting，任何 handler 侧补偿都不会被触发。
  这正是第 2、3、5 项改动的意义：把 offsetting 打开并真正喂上值。

如果将来切到完整配置（去掉 `_MINIMAL`，`rdtsc_exiting = true`），第 7、8 项改动会立刻接管，
handler 侧和硬件侧不会重复扣减（被拦截的指令在 guest 里没有执行完，TSC_OFFSET 对它不起作用）。

## 5 验证

工具：`tools/tsc_probe/main.cpp`（纯用户态，不需要驱动、不需要管理员）

```
cl /O2 /EHsc tools\tsc_probe\main.cpp
tsc_probe.exe 200000
```

输出三个数：

| 项 | 裸机参考 | 判读 |
| --- | --- | --- |
| RDTSC round-trip | 20~60 cycle | 偏高说明相邻两条 RDTSC 之间夹了 VM-exit |
| RDTSCP round-trip | 20~60 cycle | 与上一项量级差 8 倍以上 => 时间通道分裂 |
| CPUID wrapped | 100~300 cycle | 稳定上千 => CPUID 被接管（对冲没生效） |

**标准流程**：驱动未加载时跑一遍记基线 → 加载 VT 跑一遍 → 两组 CPUID 数字应当接近。
如果加载后仍稳定在 2000+ cycle，说明 `use_tsc_offsetting` 被 `ajdust_controls()` 清掉了
（部分 CPU 的 PROCBASED_CTLS 不支持），查启动日志里的
`[信息][VMCS控制位] 硬件调整后的有效控制位` 那一行，看 PRIMARY 的 bit3 是否为 1。

## 6 残余风险（P1 再做）

1. **EPT violation 的时间没有被扣**：hook 页上的访问仍然会慢一拍。这是 hidden hook 的固有代价，
   要扣就必须扣全局，会带来时钟漂移，得不偿失；建议靠减少 hook 数量解决，而不是靠对账。
2. **APERF / MPERF 仍是裸的**：`rdpmc_exiting = false`，guest 可以读到 root 期间递增的计数器，
   用 APERF/MPERF 比值能反推被虚拟化偷走的时间。这是独立于 TSC 的第二条时间通道，
   修法是给 VM-exit/VM-entry 配 MSR store/load 列表（结构体里 `msr_exit_store` / `msr_entry_load` 已经预留）。
3. **驱动可见性没变**：本次改动只处理时间，`PsLoadedModuleList`、`PiDDBCacheTable`、
   `MmUnloadedDrivers`、签名、漏驱（RTCore64 / iqvw64e）全部维持原状，
   ACE 的模块枚举与 minifilter 照样能看见这两个 `.sys`。
